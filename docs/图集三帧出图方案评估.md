## 0. 结论速览

| 项 | 结论 |
| --- | --- |
| ① 线稿示意用 AI | **不作为成品方案**。技术上可做（图生图能锁结构），但「同姿态 + 可教 + 风格绝对统一」三条不能同时保证；且**要点标注必须是矢量文本**，AI 图反而多一道返工。推荐**矢量骨架（半自动）**，100 张合计约 **100 KB**、0 元 API 费。 |
| ② 错误示范用 AI | **不建议**。模型审美先验会主动纠正「错误姿态」，产出要么不够错（不可教）、要么坏得像 AI 事故（伤观感）。推荐**正确图 + 矢量错误走向叠加**（0 元、确定性、复用线稿骨架）。 |
| ③ 200 张成本 | AI 名义 24 元 / 实付 **45–65 元**（返工），人工 19–22 h，且存"静默错姿"验收风险；矢量方案 **0 元 + 14–17 h**，风格与姿态可保证。 |
| ④ 体积 | 现 100 张封面 40 MB（1728×2304 JPEG，均值 400 KB）。若三帧都走 1728 JPEG → 每姿势 1.05 MB。矢量方案线稿 +1 KB／错误帧 +1 KB（复用封面 + CSS 滤镜）。**建议同时把封面改成 480/768/1080 WebP srcset：100 张仅 6 MB。** |
| Pilot | 8 个姿势，覆盖 8 种失效形态，**≤3 元 + 1.5–2 h**。 |

## 2. ① 线稿示意：AI 出图可行性

### 2.1 四个硬约束逐条判定

| 约束 | AI（图生图，以封面为控制图） | 判定 |
| --- | --- | --- |
| **同一姿态** | 结构由输入图锁定，躯干/四肢走向基本一致；但模型会"美化"轮廓，贴身的胳膊可能被并入躯干、屈膝被拉直 | ⚠️ 中（70–85%） |
| **同一人物** | 线稿本身不承载身份，只看发型/服装轮廓 → 该约束实际弱化，不是难点 | ✅ 可满足 |
| **白底/浅底线稿** | 常见残留：灰阶铅笔感、背景墙纹未清、大面积死黑投影 | ⚠️ 中（需阈值后处理） |
| **动作准确可教** | ❌ 最大问题。描摹照片得到的是"外形轮廓"，看不到关节角、重心线、发力方向；而教学价值恰恰在关节与重心 | ❌ 不满足 |
| **风格 100% 统一** | 每张独立生成 → 线宽、排线密度、灰度漂移；seed 只保证"同输入同输出"，不保证"跨 100 张同风格" | ❌ 不满足（需统一后处理） |

### 2.2 成功率估算（专家先验，非实测；本轮禁止生成）

| 姿态类型 | 条数 | 单次"可交付"概率 | 说明 |
| --- | --- | --- | --- |
| 全身站姿、干净背景（ST/BACK 部分） | ~30 | 0.60–0.70 | 轮廓简单、遮挡少 |
| 坐/倚/道具、有遮挡（SIT/CAFE/PROP/HOME） | ~40 | 0.45–0.55 | 手臂与躯干重叠处易糊成一团 |
| 动态/低机位（STREET/HOME 回头） | ~15 | 0.35–0.45 | 动作幅度大，模型倾向"扶正" |
| 九分身/半身（脚或腿出画） | ~18 | 0.55–0.65 | 出画边界处理不稳 |
| 特写/POV（CLOSE 8 + CAFE-04 等） | ~15 | **0.05–0.15** | 画面里根本没有全身姿态，线稿语义不成立 |

- **单张一次过**：全场加权 ≈ **0.50**
- **给 2 次机会（选优）**：≈ **0.75**；给 3 次：≈ **0.85**
- **100 张全数达标且风格一致**：≈ **0.15–0.25**（风格一致性是最短板）

> 注：上表是分布外任务的先验估计，用于预算与排期，不是验收标准。真实值必须靠 pilot 校准（见 §5）。

### 2.3 失败模式清单

| 失效模式 | 触发频率（估） | 是否可后处理修复 |
| --- | --- | --- |
| 线稿发虚 / 灰阶铅笔感、线条抖 | 高（30–40%） | 部分：阈值二值化可救，但细线会断 |
| 动作变形（手臂并入躯干、屈膝拉直、手部糊团） | 中（20–30%） | ❌ 不可修，只能重跑 |
| 风格漂移（线宽/排线/灰度不齐） | 高（跨张几乎必然） | 需全量统一后处理（≈5 h） |
| 背景未清干净（墙面纹理、地砖缝） | 中（25%） | 需人工抠除 |
| 出现文字/水印/假标注 | 低（5%） | 直接废 |

> 补充：Seedream 通道**没有独立负向词参数**（`prompt-design-system.md` §5 已记录），只能内联"画面避免…"，对"不要文字、不要灰阶"的控制力偏弱 —— 这是线稿任务的先天劣势。

### 2.4 若坚持走 AI：推荐模型与提示词策略

**最优 AI 变体是"骨架控制 i2i"**（把矢量骨架当控制图，AI 只负责上风格）：

```
模型：doubao-seedream-5-0-flash-260915（0.12 元/张）
输入：骨架 raster（白底、深灰线、实心关节点）作为 image 参考
尺寸：1728×2304 / 3:4 / jpeg / watermark=false / seed=md5(POSE-ID)
提示词（≤300 字，中文）：
「将参考图中的人体骨架示意图重绘为杂志风时装速写线稿：单色深炭灰墨线，
线条粗细均匀、收笔利落，仅保留轮廓与主要结构线，不画阴影、不画排线、
不画面料纹理，纯白背景，关节处以实心小圆点标示，人物为年轻女性，
姿态与参考图完全一致。
画面避免：灰阶过渡、铅笔颗粒、文字、数字、标注、边框、多余线条。」
后处理（必做）：二值化 → 去孤点 → 统一线宽 → 可选矢量化
```

要点：
1. **姿态由控制图保证**，AI 只买"好看"；这一步把成功率从 0.5 抬到 ~0.8，且失败只落在风格上（便宜可重试）。
2. **分品类批量跑**，同批共用同一句风格描述，减少跨张漂移。
3. **必须后处理统一**，否则 100 张摆在一起像 5 个人画的。
4. **标注层单独做**（矢量/SVG），AI 图里禁止出现文字。

> 但请注意：走这条路**骨架仍然是前置依赖**（见 §2.5）。也就是说 AI 不能省掉那 10–12 h，只是把"最终长相"从线稿换成插画感线描。值不值取决于你要的视觉调性，不取决于成本。

### 2.5 本地实测：三条替代路径的真实表现

（本轮在 `images/_eval/` 做了离线验证，未调用任何生图 API）

| 路径 | 实测结果 | 结论 |
| --- | --- | --- |
| **纯 CV 描边**（边缘检测/自适应阈值，取 ST-01） | 背景墙纹理、地砖缝、衣褶全部变成"墨团"；人物轮廓与背景噪声混在一起 | ❌ 不可用作教学图（见 `images/_eval/st01-thresh.jpg`、`st01-edges.jpg`） |
| **姿态估计 + 骨架重绘**（MediaPipe PoseLandmarker，对 100 张封面全量跑） | 5 张可直接用 / 29 张小修 / 41 张大修 / 22 张不可用 / 3 张未检出 | ✅ 姿态 100% 忠于封面，几何可核对 |
| **矢量骨架 SVG**（同一份 landmark 出 SVG） | 单张 **988 B**（gzip 484 B）；PNG 1080w 仅 15.5 KB | ✅ 体积极小、可无限缩放、可叠标注 |

**100 张姿态检测分布（`images/_eval/pose-detection-report.json`）**

| 判定 | 条数 | 含义 |
| --- | --- | --- |
| A 可直接用 | 5 | mean vis ≥0.90 且 min ≥0.60 |
| B 小修 | 29 | 拖 1–3 个关节 |
| C 大修 | 41 | 重摆半身或补遮挡肢体 |
| D 不可用 | 22 | 遮挡/出画严重 |
| X 未检出 | 3 | CAFE-04、CLOSE-06、TRAVEL-02 |

**分类看更清楚**：CLOSE 类 9/10 落在 D/未检出（特写只有脸）；CAFE 有 9 条是桌面 POV 或强遮挡。**这直接说明"线稿"对 ~15–20 条姿势在语义上不成立**，它们该给的不是人体线稿，而是**构图/机位示意**（画框线、三分线、裁切线、光源方向、主体位置）。

> 这是本轮最重要的产品发现：**线稿帧要分两种形态**——有身体的 ~80 条给骨架线稿；特写/POV 的 ~20 条给"取景示意"。混在一起做会既贵又错。

## 3. ② 错误示范：AI 出图 vs 正确图 + 标注

### 3.1 判断：**不做 AI 生图**

五条理由，按权重排序：

1. **模型先验与目标相反**。主流模型经审美对齐，"含胸驼背/双臂贴死/下巴上扬"这类描述会被主动"修复"成更顺眼的姿态。要么错得不够（学生看不出差别），要么错得离谱（关节反折、手指融团）——后者本质是 AI 事故，不是教学内容。
2. **控制力不足**。该通道无独立负向词，只能内联描述；"故意错"是要求模型**精确偏离**，比"画对"难一个量级。
3. **观感是负资产**。详情页是转化页，一帧刻意丑化的图会拉低整体调性；而"错误"真正要传达的是**偏离量**，不是"丑"。
4. **可教性差**。学生需要的是"你的手该往哪偏 5 cm"，这用一根红色虚线能说清，用一张错图反而要猜。
5. **成本效率低**。错误帧需 2.2–2.8 次调用才能凑一张能用的，而它 100% 复用线稿骨架（派生成本 ≈2–3 min/张）。

### 3.2 实测：220 条 mistakes 的错误类型分布

（`app/src/data/poses.json` 全量统计，规则聚类）

| 错误类型 | 条数 | 占比 | 最佳呈现方式 |
| --- | --- | --- | --- |
| 姿态 / 角度 | 150 | 68% | **矢量"错误走向"虚线**（从正确骨架参数化偏移） |
| 构图 / 取景 | 30 | 14% | 画框叠加（三分线/裁切区/❌ 越界区） |
| 光线 | 30 | 14% | 光源方向箭头 + 明暗区示意 |
| 其他（手部畸形、对焦等） | 10 | 5% | 局部放大 + 红圈 + 效果模拟（如眼睛区域高斯糊） |

**68% 的错误是"角度偏差"** —— 这正是矢量叠加最擅长、AI 最不擅长的部分。

### 3.3 原型证据（`images/_eval/`）

| 原型 | 做法 | 评价 |
| --- | --- | --- |
| `wrong-overlay-ST01.jpg` | 正确图上直接画红圈 + 标签 | ❌ **图文矛盾**：画面是正确姿势，标签写"错误"，用户会困惑 |
| `wrong-ghost-ST01.jpg` | 正确图去饱和压淡 + 绿色正确骨架 + 红色虚线错误走向 + 双标签 | ✅ 推荐形态：一眼看出"偏到哪"，且不出现丑图 |
| `wrong-overlay-ST01.svg` | 只存叠加层，照片复用封面 | ✅ **1033 B**（gzip 415 B），零新增照片字节 |

**推荐的错误帧定式**：

```
底色：复用封面 + CSS filter: saturate(.18) brightness(1.16)（不新增图片）
线层：SVG 叠加 —— 绿实线=正确走向，红虚线=错误走向（由骨架参数化偏移生成）
裁切：自动 zoom 到标注区（1:1 或 4:5），让这一帧与封面"看得出不一样"
文案：直接取 poses.json 的 mistakes[]（100 条已全部写好，零新增文案成本）
```

> 附带收益：`mistakes[]` 已是每姿势 2–3 条成品文案，错误帧的标注文字**不需要另写**。

### 3.4 可选增强（不是必需）

- **5–10 个高流量姿势**（ST-01/STREET-02/CAFE-01 等）做**真人实拍错误示范**：真实模特故意做错，拍摄半天可出 15–25 张。这是唯一能"既真又可控"的路径，但需签《肖像使用授权书》，V1 建议留作二期。
- 其余 90+ 姿势用矢量叠加，二者视觉上要统一（同一套红/绿色值、同字号）。

## 4. ③ 成本与工期（100×2 = 200 张）

### 4.1 三条路线横向对比

| | **A. AI 全量** | **B. 矢量骨架 + 叠加**（推荐） | **C. 混合**（B 为主 + 少量真人） |
| --- | --- | --- | --- |
| 线稿 100 张 | AI 生成 + 筛 + 统一后处理 | SVG 骨架（半自动） | 同 B |
| 错误 100 张 | AI 生成 + 筛 | SVG 叠加（派生自同一骨架） | 80 张叠加 + 20 张实拍 |
| 名义 API 费 | **24 元**（200×0.12） | **0 元** | 0 元 + 拍摄成本 |
| 实付估算（含返工） | **45–65 元**（≈420–540 次调用） | **0 元** | 拍摄 ≈0.5 天人力 |
| API 耗时 | 25–30 min（4 并发） | — | — |
| 人工：生成/绘制 | — | 10–12 h | 10–12 h |
| 人工：筛片返工 | 5–7 h | 0（所见即所得） | 0 |
| 人工：风格归一 | 5 h | 0（模板保证） | 0 |
| 人工：错误帧 | 8 h | 4–5 h（骨架派生） | 4 h + 拍摄 |
| **合计人工** | **19–22 h** | **14–17 h** | **15 h + 拍摄** |
| 新增仓库体积 | **+195 MB**（65 MB × 3 份副本） | **+0.6 MB** | +0.6 MB |
| 交付一致性 | 中低（逐张独立） | **高（同一模板）** | 高 |
| 验收风险 | **静默错姿**（错图当教具） | 低（画的时候就能看出对错） | 中（实拍需审） |
| 可维护性 | 改一处要重跑 | 改模板全量重出 | 中 |

### 4.2 为什么 AI 反而不省钱

- 名义 24 元只是"一次全中"的价；按 §2.2 概率，线稿需 ≈1.7 次/张、错误需 ≈2.5 次/张 → **420 次 ≈ 50 元**（不含 pro 升级与输入项）。
- 真正的成本在**人工**：200 张筛片 5–7 h + 100 张风格归一 5 h = 10–12 h，正好抵掉矢量方案的绘制时间，却换来更差的一致性。
- 更要命的是**验收风险**：线稿一旦姿势轻微走形，它会以"教学资产"的身份长期线上存在 —— **错的教具比缺的教具更坏**。缺图至少有"制作中"占位，语义是诚实的。

| 姿态忠实度 | 8/8 骨架与封面关键关节偏差可在原图上肉眼核对通过 |

## 5. ④ 图片体积与加载预算

### 5.1 实测压缩数据（Pillow，取 12 张封面样本）

| 尺寸 | WebP q82 | JPEG q80 | 现状 |
| --- | --- | --- | --- |
| 480×640 | **31 KB** | 42 KB | — |
| 720×960 | **60 KB** | 84 KB | 详情页展示宽 720 |
| 1080×1440 | **113 KB** | 169 KB | 3× 屏 |
| 1728×2304 | 225 KB | 333 KB | **现网均值 400 KB** |

线稿资产（实测）：SVG **988 B**（gzip 484 B）／PNG 1080w 15.5 KB／WebP 9.1 KB。
错误帧叠加 SVG：**1033 B**（gzip 415 B）。

### 5.2 三帧的页面预算

| 方案 | 单姿势三帧总量 | 100 姿势增量 | 详情页首帧 |
| --- | --- | --- | --- |
| 现状（后两帧占位） | 封面 400 KB | — | 400 KB |
| 三帧全 1728 JPEG（AI 路线） | 400 + 200 + 450 = **1.05 MB** | **+65 MB** | 400 KB |
| 矢量（推荐） | 封面 + 1 KB + 1 KB = **≈402 KB** | **+0.2 MB** | 400 KB（可降档） |
| 矢量 + 封面改 WebP srcset | 113 + 1 + 1 = **115 KB** | **−34 MB** | **113 KB** |

> 详情页现实现是"一次只渲染一帧"（`PoseDetailView.vue` 单个 `<img>` 绑定当前 frame），所以三帧不会同时下载 —— 这点已经是好的，预算按"单帧"算即可。

### 5.3 现有 40 MB 的三个坏消息

1. **每张 400 KB 是不必要的**：同图 1080 WebP 仅 113 KB，肉眼在 3× 屏上无差别。
2. **同一批图存了 3 份**：`images/*.jpg` 38 MB + `app/public/poses/` 40 MB + `app/dist/poses/` 40 MB ≈ **118 MB**，仓库总量 293 MB。
3. **没有 srcset**：首屏 8 张卡片全量拉 1728 原图 ≈ 3.2 MB（改 480w WebP 后 ≈ 248 KB）。

### 5.4 落地建议（按性价比排序）

| 优先级 | 动作 | 收益 |
| --- | --- | --- |
| P0 | 三帧走矢量（线稿 SVG + 错误叠加 SVG） | 增量从 +65 MB 降到 +0.2 MB |
| P0 | 封面产 480/768/1080 三档 WebP + srcset，`<img>` 保留 JPEG 兜底 | 100 张 40 MB → **6 MB**；首屏 3.2 MB → 248 KB |
| P1 | 扩展 `app/scripts/build_data.py`：只产派生图，不再把原图复制进 `public/`；`dist/` 不入库 | 仓库 −80 MB |
| P1 | 详情页首帧 `preload`，`lineArt`/`wrong` 点击后再注入 | 三帧切换增量 ≈0 |
| P2 | `<img>` 补 `sizes` 与固定宽高比（现已有 720×960，CLS 已 OK） | 保持 LCP 稳定 |

**定向预算线**：`app/dist` ≤ 8 MB；详情页首屏 ≤ 150 KB；三帧切换增量 ≤ 20 KB；单张线稿 ≤ 20 KB。

## 6. 方案对比总表（决策用）

| 维度 | A. AI 线稿 + AI 错图 | B. 矢量骨架 + 矢量叠加 | C. B + 少数实拍错图 |
| --- | --- | --- | --- |
| 姿态准确性 | 中（i2i 可锁，仍会走形） | **高（点对点可核对）** | 高 |
| 动作"可教"性 | 低（只有轮廓） | **高（关节/重心/偏离量）** | 高 |
| 同人物 | 弱相关（线稿不承载身份） | 不适用 | 不适用 |
| 白底/浅底可控 | 中（需阈值后处理） | **100%** | — |
| 风格一致性 | 低（逐张漂移） | **高（模板）** | 高 |
| 新增体积 | +65 MB | **+0.2 MB** | +0.2 MB |
| API 费 | 45–65 元 | **0 元** | 0 元 |
| 人工 | 19–22 h | **14–17 h** | 15 h + 拍摄 |
| 改版成本 | 重跑 | **改模板即重出** | 中 |
| 主要风险 | 静默错姿、观感失控 | 绘制期投入前置 | 肖像授权 |

### 推荐：**B**，理由三条
1. **教学资产的第一要求是"不错"**。矢量骨架的姿态来自封面关键点，可逐点核对；AI 线稿的偏差无法事前发现，只能靠人眼抽查 200 张。
2. **线稿帧与错误帧共用一套骨架**。错误帧 = 骨架参数化偏移（如手臂向躯干收 60%）+ `mistakes[]` 文案，边际成本 2–3 min/张。**AI 路线反而要付两份生成 + 两份筛片。**
3. **体积就是产品体验**。100 张线稿合计 100 KB，等于免费；AI 光栅线稿会让详情页每帧多 200 KB，且要背 65 MB 仓库增量。

### A 的位置
A 不是"错"，而是**贵且不可控**。唯一值得保留的用法是 §2.4 的"骨架控制 i2i"：**先有骨架，再用 AI 换风格**。若最终定调要"插画感线描"而非"工程线稿"，按此路线做，成本仍以骨架为主。

## 8. 本轮未验证 / 风险声明

1. **本轮零生成**：未调用 arkcli，故概率估计（§2.2）为专家先验，须由 pilot 校准。arkcli 在本沙箱因 `state_migration` 无法执行（`~/.arkcli-bytecloud` 无写权限），不构成阻塞 —— 生成需用户单独批准并在正常环境执行。
